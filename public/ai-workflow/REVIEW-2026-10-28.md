# AI 工作流审查记录 2026-10-28

> 结合最新行业趋势（2026-05 ~ 2026-10 的 feed 收录）与一线开发者分享，对 `global/data.js`、`local/customizations.js`、README 中的范式、管线、工具链与本地定制做的一次修正性审视。

## 总判断

`feed` 层已经是最新的——它自己就收录了 2026 年的全部修正信号；但上面的「结构化层」（paradigms / pipeline / toolchain / Local 定制）没有吸收这些信号，还停留在 2025 年上半年的认知框架里。

**核心结论：需要修正的不是「信息没收集到」，而是「收集到的信息没反哺回范式、管线和工具选型」。**

---

## 一、范式层（paradigms）

### 1. 缺「Agentic Engineering」这个 2026 年的主轴范式

- **现状**：paradigms 只有 5 个，且「Agent-Driven Development」被描述成「AI Agent 自主完成端到端任务」的**工具能力**。
- **问题**：f43、f105 已写明——Karpathy 2026-02 宣布 Vibe Coding 过时，取而代之的是 **Agentic Engineering**，定义是「*协调有缺陷的 Agent、同时保持正确性/安全性/品控/可维护性的专业学科*」。这与「Agent-Driven Development」不是一回事：前者是「让 AI 自己干」，后者是「人如何驾驭一堆会出错的 Agent」。
- **建议**：新增顶层范式 `agentic-engineering`，keyPractices 含「人机协作模式（Supervisor / Collaborative / Autonomous，见 f71）」「HITL 门控」「验证优先」；原「Agent-Driven Development」降级为其子模式。

### 2. Vibe Coding 的成熟度标签和风险描述是旧的

- **现状**：`vibe-coding` 标 `emerging`，risks 是「代码质量参差不齐 / 安全漏洞 / 过度依赖」这类泛泛之词。
- **问题**：f43（已过时）、f96（METR 实证慢 19% 却自认快 24%）、f99（GitClear 代码搅动率翻倍至 7%）已把风险具体化、量化。标 `emerging` 是误导。
- **建议**：成熟度改 `legacy/entry`，定位成「原型与内部工具阶段的快速试错范式，进入生产前必须升级为 Spec-first / Agentic Engineering」。risks 换成：感知-实际效率差、代码搅动、验证税。

### 3. 「AI Pair Programming = mainstream」需要祛魅

- **现状**：`ai-pair-programming` 标 `mainstream`，叙事是「人类导航、AI 驱动」的 rosy 结对模式。
- **问题**：f99、f53 已收录祛魅证据——84% 自认提效但 27% 体验变差、METR 实测反而慢 19%。「导航者/驱动者」这套 2024 叙事已被「Supervisor（定规格、Agent 执行、提交前审查）」取代（f71）。
- **建议**：保留范式但改叙事，标注「主流但有祛魅修正」，keyPractices 补「完全认知所有权（f99）」「首轮说清意图+约束+验收标准、批量发送（f36）」。

### 4. Test-Driven AI 被低估

- **现状**：`test-driven-ai` 标 `growing`。
- **问题**：2026 年第一共识恰恰是「验证优先」——Anthropic 官方列为影响力最大的单一实践（f100/f82/f8），Superpowers 靠 TDD 驱动冲到 24 万星（f37），Appwrite 列「测试先行」为七大趋势之一（f87）。
- **建议**：升为 `mainstream/core`，并与管线「验证优先」打通——测试用例是编码**之前**的验收合约，而非 s4 阶段产物。

## 二、管线层（pipeline）

### 5. 六阶段是「传统 SDLC + AI 贴片」，不是「验证优先闭环」

- **现状**：需求理解 → 技术设计 → 编码 → 测试 → 部署 → 迭代；测试（s4）排在编码（s3）**之后**。
- **问题**：最硬共识是 **Plan-Then-Execute + 验证优先**（f100/f82/f94/f90/f37）：验收标准要在编码前写进 prompt，给 AI 可运行的检查（test/build/lint/截图 diff）让它自收敛，而非主观声称「看起来好了」。
- **建议**：至少改为 **探索(Explore) → 计划(Plan) → 编码(Implement) → 验证(Verify) → 提交(Commit)**，或在 s3 前插入「验证策略定义」的显式步骤。

### 6. 缺「上下文工程」这个横向核心技能

- **现状**：全篇只有 Local `corePoints` 的「精简上下文」，还被埋在 customizations 里。
- **问题**：Appwrite 列为「核心技能」（f87），Anthropic 说「上下文窗口是首要资源、填充会致退化」（f100）。
- **建议**：加「跨阶段能力」维度，单独列「上下文工程」——规则文件分层、CLAUDE.md 精简、Skills 按需加载、Subagent 隔离中间探索（f72/f95/f54）。

### 7. 缺「HITL 门控 / 审批门控」显式机制

- **现状**：每 stage 有 `humanRole`，但无「高风险节点必须暂停等人确认」的形式化门控。
- **问题**：f93（带人工审批门控）、f92（HITL 关键决策点）、f97（HITL 成高风险企业应用强制 UX 模式）都把「门控」列为生产级四大模式之首。
- **建议**：给部署/发布、编码中的「不可逆操作」显式标注「人工审批门控」，与 `humanRole` 区分——角色是「谁负责」，门控是「哪里必须停」。

### 8. 缺「安全 / 提示注入」专门防线

- **现状**：s4 tips 仅一句「AI Review 重点关注安全漏洞」。
- **问题**：f97（间接提示注入、约 1/8 安全事故源自自主 Agent、零信任前端）、f96（45% AI 代码含 OWASP Top10、86% 样本有 XSS）、f79（AI 代码 bug 比人类高 1.7 倍）都指向：安全不能靠 Review 兜底，而要前置。
- **建议**：加「安全边界」维度，直接引用 Green/Red Zone 边界（f96：认证授权/数据校验/金融合规必须人类主导）+ 零信任前端（f97）。

## 三、工具链层（toolchain）

### 9. 缺 Codex，且工具是「选一个」而非「分工」

- **现状**：列了 Cursor / Claude Code / Copilot / TRAE SOLO / Windsurf / Aider，**没有 OpenAI Codex**。
- **问题**：f95 已给出答案——工具是**三层生态分工**：Cursor 赢 IDE 内联编辑、Codex 赢大规模并行任务、Claude Code 赢 Agent 编排。
- **建议**：工具链从「横向并列选型」改成「分层分工矩阵」，补 Codex，写进「三型分工而非竞争」。

### 10. 缺 MCP 层

- **现状**：只有「AI编码工具 / AI Agent平台 / 测试与质量」三类。
- **问题**：MCP 已是「统一上下文层」「Agent 工具连接标准」「2000+ 服务器」（f81/f106/f97/f76）。
- **建议**：加「上下文与集成层」类目，MCP（+ Skills/Hooks/Subagents 四大定制机制）单独成类。

### 11. Devin 评级可能低估

- **现状**：Devin ⭐⭐⭐。
- **问题**：f47/f104 里 Devin 2.0 任务完成度 95% 领跑、P1 故障修复 43 分钟 vs 人类 4.2 小时。
- **建议**：评级可补「能力最强但 Enterprise 定价贵」。

## 四、Local 定制层（customizations.js）

### 12. 「精简上下文」那句自相矛盾的话

- **现状**（customizations.js:127-134）：「Prompt 保留必要冗余，以便模型全面理解」。
- **问题**：与下一句「避免无关信息干扰」打架，也与 f100「上下文是首要资源、填充会致退化」直接相悖。
- **建议**：删掉或改成「只保留完成任务所必需的最小上下文，冗余信息会稀释注意力」。

### 13. 「多模型交叉验证」是 naive 版本

- **现状**（`wf-multi-model`）：「同一需求用不同模型分别实现，取最优方案或融合优点」。
- **问题**：最贵做法。f87/f95 给出的是**角色化分层选型**：快便宜模型做样板、前沿模型做架构、专项模型做安全 Review。
- **建议**：改成「多模型分层路由」——按任务类型路由到合适模型，而非同题异构再融合。

### 14. 缺「小批量/原子提交」的反制纪律

- **现状**：`wf-commit` 只讲「自动生成提交信息」，无提交频率/粒度纪律。
- **问题**：f99 指出——AI 让「小批量提交」瓦解，代码搅动率翻倍。这是 AI 编码特有的副作用。
- **建议**：补「改完一个功能、验证通过就提交，保持 diff 可审查（每次 3-5 文件）」（f90 原子化迭代纪律）。

### 15. lf1「效率提升 40%」自报数据要打问号

- **现状**：localFeed lf1「人均代码产出提升 40%、Code Review 通过率 65%→82%」。
- **问题**：f53/f99 实证反复打脸——感知快 24% 但实际慢 19%，39 个百分点落差。无对照基准的自报数据可能重蹈覆辙。
- **建议**：标注数据来源与测量方法，或补「建议用 METR 式对照实验复核」。

## 五、其他零散

- **meta.version 停在 1.0.0**，lastUpdated 却到了 2026-10-05——建议引入有意义版本递增（范式层每动一次 bump 一次）。
- **feed 的 id 顺序乱**（f108 到 f1 乱序，f1-f12 后补却排最尾）——建议按 date 排序或重建 id。
- **`AutoGPT` / `MetaGPT` 仍挂在 agent-driven-dev 的 tools 里**——2023-2024 遗留，应换成 Codex、Goose 等活跃工具。
- **README 写「通过 OpenClaw cron」**——当前环境已可用 Claude Code 内置 Cron 工具（`CronCreate` 等），自动化触发方式可顺带更新。
