六阶段适合说明交付全貌；个人完成一个任务时可使用更短的循环。二者是不同观察尺度，无需竞争哪一个才是正确管线。稳定 ID 属于页面维护约束，不应限制方法论的表达。

## 2. 当前可以采用的核心主张

**把 AI 编程组织为：明确任务 → 提供相关上下文 → 小步执行 → 获得真实反馈 → 审查交付 → 沉淀经验。**

这里的 Agentic Engineering，作为本文的工作定义，是开发者组织 Agent 完成工程任务，并对目标、验证和交付负责。它适合作为分享总主题，但不必证明某个术语已经“取代”另一个术语。

这是一套根据下述资料综合出的个人实践建议。不同来源的经验相互支持，不等于受控实验已经证明每个步骤都能提效。产品能力与命令会变化，本文优先保留方法；实际操作以所用版本和项目规则为准。

### 2.1 头部公司的经验，如何转成个人动作

| 一手来源 | 可以借鉴的方法 | 我们可以怎么用 | 不宜直接推广的部分 |
| --- | --- | --- | --- |
| [OpenAI：Harness engineering，2026-02-11](https://openai.com/index/harness-engineering/) | 让仓库知识可发现，让应用、日志和验证反馈可被 Agent 使用 | 给项目提供简短入口、运行方式和可靠检查；反复失败时找缺失的信息或能力 | 新建内部产品的实验；不能把其速度估计、免人工逐个审 PR 或全自动目标搬到所有存量业务 |
| [Anthropic：长任务执行环境，2025-11-26](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) | 单功能增量推进，留下进度与 Git 记录，通过浏览器检验真实行为 | 长任务记录已做/未做/如何验证；换会话后先恢复状态 | 其具体模型、初始化流程和文件形式是实验方案，不必照搬为每个小任务的仪式 |
| [Anthropic：长任务应用开发，2026-03-24](https://www.anthropic.com/research/harness-design-long-running-apps) | 将评价标准具体化，必要时分离生成与评价 | UI 先定义布局、状态和交互标准；复杂变更增加针对性复核 | 多 Agent 和多轮评估会增加时间、费用与复杂度；自评分升高不等于用户更满意 |

上述案例共同提示：除了模型本身，还要改善 Agent 获取信息、采取行动和判断结果的环境。个人起步只需把项目跑得起来、把需求说明白、把关键行为验得到，无需先搭建复杂平台。

### 2.3 哪些说法不应出现在分享结论里

- “某范式已经过时”“某工具能力最强”：缺少明确范围和可比较依据时，改讲任务适配。
- “用了 AI，代码更多，因此更高效”：应核对是否更快交付可接受结果，以及审查、返工是否增加。
- “多个模型都同意，所以正确”：仍需契约、复现、测试或实际运行证据。
- “Spec 写清了，就不用审查实现”：规格、实现和验证都有可能出错。
- “所有任务都先写长计划、都上 TDD、都开多个 Agent”：应按不确定性、风险和验证成本选择。

METR 的 2025 实验和 2026 后续更新说明，任务、工具、参与者和测量方式会改变结论。后续研究存在选择偏差与并行计时难题，不能把任何单一提效百分比作为所有人的预期。[METR 更新，2026-02-24](https://metr.org/blog/2026-02-24-uplift-update/)

## 3. 拿到任务后，先选工作方式

以下是建议起点，按实际任务调整，不是行业标准。

| 任务 | 怎么开始 | 主要验收方式 | 什么时候升级处理 |
| --- | --- | --- | --- |
| 文案、小样式、明确的小修改 | 给目标、位置、限制，直接执行 | 定向 diff、相关页面或构建检查 | 发现跨模块行为影响时补计划 |
| 列表、表单、业务页面 | 读参考实现、接口契约与设计；列短计划 | 类型/构建、关键交互、空态/错误态、视觉核对 | 业务规则缺失时找产品或领域负责人澄清 |
| Bug 修复 | 先复现，收集实际与预期差异 | 原失败场景修复及相关回归；适用时写回归测试 | 反复猜测无新证据时停止改代码，回到诊断 |
| 重构、RN→H5 迁移 | 明确要保留的行为、调用方和影响范围 | 行为对照、契约、关键路径，审查不必要改动 | 兼容性或数据语义不清时先拆小任务 |
| 跨模块新功能、复杂架构调整 | 单独探索，写简短 Spec 与验证计划 | 分批集成、端到端场景、必要的独立复核 | 范围持续扩大时重新划定边界 |
| 权限、资金、生产数据相关改动 | 先明确业务责任、环境与授权范围 | 领域检查、异常路径、发布与恢复验证 | 涉及不可逆操作或越权时必须先解决授权 |

选用自己熟悉、公司允许的一个主力工具建立基线。只有遇到具体限制，再比较另一工具或模型。不要为了展示先进性，同时引入多个 IDE、MCP 服务和编排层。

## 4. 每个任务使用的最小闭环

### 4.1 先把需求写成可验收的任务

任务卡可以直接写在对话里；复杂或跨会话任务再保存到仓库。下面是可复用模板，方括号内容按项目填写。

```text
目标：[谁在什么场景完成什么事情]
范围：[要改什么；这次不改什么]
参考：[现有实现、设计、接口或业务说明及版本]
约束：[项目规则、依赖限制、兼容要求]
验收：[正常路径、重要边界、异常路径分别应该怎样]
验证：[实际可用的检查命令、浏览器步骤或人工核对方式]
执行边界：[允许编辑/运行的范围；需要另行授权的操作]

先核对相关代码与已有约定。简单任务可直接实施；复杂任务先列短计划。
发现会影响业务结果的关键歧义时明确指出，不自行编造。
完成时说明改动、实际检查结果、未验证项和剩余问题。
```

测试工具和命令从项目读取，不能把博客的构建命令写成所有业务项目的标准。验收描述应能由另一个人独立判断，不只写“正常”“完整”“符合最佳实践”。

### 4.2 让 Agent 读取足够的信息

优先提供一份相邻的正确实现、接口定义、相关规则和具体错误信息。截图用于布局和视觉对照，结构化接口用于字段与契约；二者不能互相替代。从可访问的原始文档或导出文件获取信息，缺失信息明确标注。

上下文不追求最短，而要相关、完整、可追溯。长期规则保存项目不易从代码推断的约定；本次临时要求留在任务里。不要把每次纠错未经判断就追加为全局规则。

### 4.3 先完成一个能验证的切片

例如列表页先完成“请求 → 数据转换 → 展示 → 一个筛选条件”，通过检查后再补其他状态。按一个完整行为拆分，比按“AI 先写完所有文件”更容易发现契约误解。

对可表达为自动测试的行为修复，可采用先复现失败、再最小修复的 TDD 路径。纯视觉调整可用截图、浏览器与人工对照；不为形式完整编写只复述实现的测试。

### 4.4 验证结果，再审查差异

| 要回答的问题 | 合适的证据 | 证据的局限 |
| --- | --- | --- |
| 能否被项目接受？ | 类型、lint、构建及项目必需检查 | 通过构建不代表业务正确 |
| 关键行为是否正确？ | 针对验收条件的测试、接口结果与浏览器操作 | Mock 通过不等于真实接口已联调 |
| 页面是否符合预期？ | 目标尺寸下的截图、状态与交互对照 | 截图不能证明所有交互和可访问性 |
| 是否引入不必要代价？ | diff、调用方、依赖和复杂度审查 | 模型审查可能遗漏问题，关键语义仍需人理解 |

保留原有 Simplify / Review / Verify 思路，但不把简化当成每次必须大改的步骤：先得到可运行基线，再做必要简化，改动后重跑受影响检查。复核输入应包含需求和验收，不仅是生成者的解释。

人至少应能解释关键业务规则、数据流、失败方式，以及为什么现有证据足以接受这次变更。对于无法解释的关键行为，先让 Agent 结合代码演示和说明，再决定能否交付。

### 4.5 交付与沉淀

完成记录至少包含：变更用途、验证结果、未验证项、剩余风险。按项目规则提交一个可审查、可回退的完整改动；不以固定文件数衡量原子性。

长任务额外留下当前进度、关键决定、相关文件、已运行检查和下一步。生产发布、数据写入和权限变化按已有授权边界执行，不能由“实现完成”自动推导出“可以发布”。

## 5. 一个可用于个人实践和公司演示的完整案例

**示例任务：给已有售后工单列表增加状态筛选。** 这是教学场景，不是已完成项目的业绩描述。具体字段、接口和路径需由真实项目替换。

**任务输入。** 指定列表入口、一个已正确实现筛选的参考页面、接口字段与状态枚举；要求保留原分页和错误处理。未知枚举或分页约定先查契约，不猜字段。

**验收条件。** 切换筛选后请求参数符合接口；页码按约定重置；清空恢复默认列表；空结果有空态；请求失败可恢复；快速连续切换时旧响应不能覆盖当前结果；目标尺寸下操作可用。

**执行顺序。** Agent 先追踪现有请求和状态管理，确认可以复用的能力；实现一个筛选值的完整链路，再扩展枚举与状态。先核实请求库已有的竞态处理，避免重复引入机制。业务含义由开发者确认。

**验证与展示。** 使用受控测试数据，展示一次正常筛选、清空、空结果、失败恢复及快速切换。解释实际发出了什么请求、返回的数据如何影响页面；不能只展示最终截图。缺少后端环境时说明本轮仅完成 Mock 验证，真实联调列为交付前待办。

**复盘。** 对照原始 diff，指出 Agent 复用了什么、哪里理解错了、哪些修改被拒绝、用什么证据确认修复。若任务没有出现实际失败，不编造事故；可另设一个明确标注的教学反例演示检查如何发现问题。

已有原型→接口→代码实践可接入同一闭环：读取原型 → 获取接口契约 → 定义行为与验收 → 生成 → 浏览器核对 → 交付。是否先补 Figma 设计稿取决于任务需要，不把额外设计产物作为所有页面的强制前提。

## 6. 失败时怎么调整，什么时候使用进阶能力

| 现象 | 优先调整 | 进阶选项 |
| --- | --- | --- |
| 改了几轮还在猜 | 补复现、日志、预期与实际差异，缩小范围 | 有明确瓶颈时换模型或请独立诊断 |
| 代码符合语法但业务错误 | 补业务反例和契约，重新审查验收条件 | 邀请领域负责人核对，不能靠模型投票 |
| 对话越长越偏 | 保存状态与决定，清理无关背景再继续 | 用明确交接开启新会话；不按固定百分比机械清空 |
| 多任务互相覆盖或冲突 | 拆清依赖与文件责任，先统一接口 | 独立任务再用 worktree/子 Agent，集成后统一验证 |
| UI 总是“看起来差不多” | 给具体布局、间距、状态和交互标准 | 独立视觉复核；允许设计判断保留主观性 |
| 同类错误持续发生 | 判断是规则缺失、检查缺失还是工具不可用 | 分别沉淀为规则、确定性检查或可复用流程 |

MCP 用于需要连接外部工具与资源的任务；Skills 用于重复出现的专业流程；Hooks 适合工具支持的确定性检查节点；Subagents 适合可隔离的探索或复核。使用前说明它解决哪个实际问题，并确认权限、支持范围和维护成本。

建议在任务开始时设一个可调整的试验预算，例如同一问题连续两轮无新证据就暂停盲目重试，回到复现与诊断。次数是个人管理策略，不是模型能力定律；正式上线检查也不能因为预算用尽而跳过。

## 7. 个人实践：两周建立第一份可比较记录

以下是建议节奏，不是预设有效的实验结论，也不是定时任务安排。

**第一周：跑通基线。** 选几个真实且边界清晰的任务，覆盖小修改、业务功能和 Bug 修复。使用同一个主力工具及上述闭环；当天记录一次主要失误或顺畅之处。

**第二周：只改一个因素。** 根据上周的主要问题，选择补验收条件、引入更好的参考实现、增加浏览器验证或增加独立复核中的一项。选择相近任务观察效果，不同时更换工具、模型和全部流程。

```text
日期 / 项目 / 任务类型：
工具与模型版本（可确认时）：
本次采用的方法或改变：
人工投入：需求澄清 + 实施干预 + 审查 + 返工
从开始到验收的总历时（并行任务单独标注）：
实际通过的验收 / 未验证项：
发现的缺陷、额外成本与后续返工：
一次有效做法 / 一次无效做法：
下次保留、调整或停止什么：
```

不要求个人先做正式随机对照试验。小样本可以支撑“我在这些任务上更顺畅”的经验判断，不能推出整个团队提效百分比。历史任务估时、主观节省时间和实际计时分别记录；不要用估算包装成观测结果。

规则的状态采用“准备尝试 → 实践记录 → 个人默认 → 待复核/停用”。跨工具或模型升级后抽查关键实践；如果多次增加审查和维护负担却无可见收益，就简化或停用。

## 8. 公司分享：用一个任务讲清方法

建议主题：**《从让 AI 写代码，到把任务可靠交付：我的 AI 编程实践与迭代》**。在积累案例前，副标题使用“实践方案与试点”，避免把建议写成已经验证的成绩。

| 建议时长 | 内容 | 观众应获得什么 |
| --- | --- | --- |
| 3 分钟 | 一个真实困扰：生成快，但需求理解、验证或返工卡住 | 明确本次分享要解决的问题 |
| 5 分钟 | 领袖经验与公司案例中可借鉴的动作 | 理解方法来源及适用限制 |
| 12 分钟 | 演示工单筛选或同等真实任务：任务卡→实现→验证→diff | 能照着完成一个自己的任务 |
| 5 分钟 | 展示失败、修正与取舍，说明仍未验证的部分 | 知道何时信任、何时介入 |
| 5 分钟 | 同事选择一个任务，补验收条件并讨论适配 | 把分享转成可试用的下一步 |

演示准备一份脱敏代码、受控数据和录屏备份，确认公司允许展示的范围。效果数字只使用有记录的数据；工具名单不做排行榜，同行经验也不写成公司统一要求。

交流重点：什么任务适合直接执行，什么任务需要计划？同一失败发生在需求、上下文、执行还是验证？某个额外步骤是否值得它的成本？收集同事实际使用后的反例，作为下一版输入。

## 9. 对现有博客的升级规划

保留 Global / Local 的基本结构，但明确其读者价值：**Global 提供带来源的方法与选择依据；Local 展示自己的跨项目操作、案例和迭代。** 工具和信息流支持这条主线。

| 页面模块 | 建议变化 | 内容验收 |
| --- | --- | --- |
| 首页/总览 | 用核心闭环和一个任务选择入口开场 | 新读者能快速知道下一步怎么做 |
| Global 管线 | 保留交付六阶段，突出任务内的实施—验证回路 | 阶段有输入、动作和完成证据 |
| Global 范式 | 按协作方式与实践方法解释关系，弱化无依据成熟度评级 | 不暗示自主程度等于工程质量 |
| Global 工具 | 展示能力、适用任务、限制、来源和核实日期，补 Codex 覆盖 | 不靠星级或未核实价格决定推荐 |
| Local 常规工作流 | 将计划与验收移到生成前，加入任务卡和失败处理 | 用户可直接选一个任务照做 |
| Local 技能与案例 | 标注适用业务项目、经验状态、输入/过程/证据/局限 | 不把示例、试验和成绩混在一起 |
| 信息流 | 作为可追溯阅读材料，链接到受其影响的实践 | 读完能理解它改变了哪条方法 |

**第一批：内容优先。** 修正已知错误与过度承诺，补一手来源、核心闭环、任务卡及教学案例；公开示例中的疑似凭证问题仍立即处理。验收标准是同事读完可以发起一个明确任务。

**第二批：实际记录。** 跑两周个人试点，用真实案例补上耗时、失误和验证结果；再组织公司交流。验收标准是能区分“建议这样做”和“我已经这样做过”。

**第三批：按需要维护页面。** 执行 v2 中适用的数据兼容、排序、更新时间和输出安全修正。自动抓取没有立即价值时可以继续半自动维护；开启外部自动导入前必须完成对应安全检查。实施这些技术事项不应阻塞个人开始实践。

本次产出为文档核对与升级方案，尚未更新博客页面或验证实践收益。下一轮应由真实任务记录推动内容变化，而非再增加一批术语。
