# AI 工作流审查与升级规划 v2

> 审查日期：2026-10-28
>
> 审查基线：[原审查记录](./REVIEW-2026-10-28.md)及当前仓库实现。
>
> 文档状态：升级建议与实施验收方案；本文不代表相关代码已经修改。
>
> 适用范围：`public/ai-workflow/` 的 Global 知识层、Local 实践层、展示页面与信息更新链路。

## 1. 审查结论

原规划关于验收前置、上下文管理、权限控制和工具评估的方向合理，但**不适合原样执行**。主要问题有三类：

1. **证据强度不足**：把 feed 中的二手报道当成已验证事实，用局部实验、流行术语和工具热度推导行业共识与工具排名。
2. **部分现状判断不准确**：现有管线已经在需求阶段产出验收标准；Local 已包含原子提交要求；也已有生产发布审批文字。
3. **实施链路不完整**：没有处理页面字段兼容、Local 引用、抓取脚本占位、更新时间失真，以及外部内容进入页面时的安全边界。

升级目标应是：**让每条实践可追溯、每个任务可验收、每次授权有边界、每次更新有真实依据。** 新范式名称和工具分类服务于这个目标，不作为升级成效本身。

建议先修正事实与公开示例，再增强现有六阶段管线，最后迭代分类和工具评估。保留原审查文档作为历史记录，以本文作为后续实施依据。

## 3. 对原规划的逐项裁定

| 原项 | 裁定 | 升级后的处理方式 |
| --- | --- | --- |
| 1. 新增 Agentic Engineering 顶层范式 | 调整后采纳 | 作为工程原则总览；结对、自主执行属于协作模式，Spec/TDD 属于实践方法，避免不同维度互相替代 |
| 2. Vibe Coding 改为 legacy/entry | 不采纳该标签 | 原型适用性与成熟度分开描述；不凭术语变化宣告过时，也不把内部工具自动视为低风险 |
| 3. AI Pair Programming 需要祛魅 | 部分采纳 | 补理解成本、审查责任和适用场景；“主流”与“可能低效”不矛盾，无证据说明监督模式全面取代结对 |
| 4. Test-Driven AI 升为 mainstream/core | 调整后采纳 | 将验证前置作为团队默认原则；TDD 按行为可测试性采用，不以星数证明行业普及率 |
| 5. 六阶段改为五阶段 | 不采纳替换方案 | 保留发布、运行反馈；增强 s1/s2 的验收设计和 s3/s4 的验证闭环 |
| 6. 上下文工程成为横向能力 | 采纳 | 补相关性、完整性、来源、版本、权限与任务交接，不追求上下文绝对最短 |
| 7. HITL 门控 | 细化后采纳 | 补触发条件、批准者、授权范围、证据与失效条件；已有明确授权时不重复确认 |
| 8. 安全与提示注入防线 | 调整后采纳 | 优先保护开发 Agent 的工具权限和凭证；产品运行时 Generative UI 风险另列适用条件 |
| 9. 补 Codex、改分工矩阵 | 部分采纳 | 补工具覆盖缺口；按任务能力与实测评估，不固定三个品牌各占一个层级 |
| 10. 增加 MCP 层 | 调整后采纳 | 定义为可选集成方式；MCP、Skills、Hooks、Subagents 分别建模，不视为同一种标准 |
| 11. 提高 Devin 评级 | 暂缓 | 完成率、故障修复时间未追溯到可比较评测，暂不据此提高评级或声称“能力最强” |
| 12. 删除“必要冗余” | 修改表述 | 保留必要业务解释、反例和约束，清除重复过时材料；不能把信息完整性等同于冗余 |
| 13. 多模型交叉验证改分层路由 | 调整后采纳 | 日常采用单工具基线；按难度与质量升级模型，关键任务仍可做有针对性的独立复核 |
| 14. 补原子提交纪律 | 修正现状判断 | `wf-worktree` 已有要求；加强与 `wf-commit` 的衔接，不新增“每次 3–5 文件”硬限制 |
| 15. lf1 的 40% 数据补来源 | 采纳 | 未证实前标为待核实，不作提效结论；代码产出增加也不等于交付效率提高 |
| 其他：版本、排序、旧工具、调度器 | 部分采纳 | 稳定 ID 不重建；版本区分结构与内容；工具按维护状态核实；调度保持中立，先处理抓取脚本占位 |

### 3.1 必须修正的外部证据解释

**METR 数字存在混用。** 2025 年研究覆盖 16 名熟悉自身开源项目的开发者、246 个任务，主要使用当时的 Cursor Pro 和 Claude 3.5/3.7 Sonnet。任务前预计耗时减少 24%，任务后感知耗时减少 20%，实际耗时增加 19%。原文“慢 19% 却自认快 24%”混用了任务前预期与任务后感知；所谓 39 个百分点也只能描述事后感知与观测的耗时变化差，不能称为一般生产率差。[原始研究](https://arxiv.org/abs/2507.09089)

METR 在 2026-02 的后续更新指出，新实验存在参与者选择偏差和并行任务计时问题，对当前提效幅度只能提供很弱的证据。因此，不能用旧研究证明“2026 年 AI 普遍降低效率”，也不能用新数据宣布普遍提效。[METR 后续更新](https://metr.org/blog/2026-02-24-uplift-update/)

**暂不作为升级依据的数字**包括“45% AI 代码含漏洞”“86% 样本有 XSS”“1/8 安全事故来自 Agent”“Devin 完成率 95%”“P1 修复 43 分钟”“代码搅动率翻倍”和工具星数。它们并非已被本次审查判定为错误，而是缺少已核实的样本、分母、测量时期、比较条件或原始出处。追溯前不得直接推导工具排名、总体风险或因果关系。

**工程建议可以成立，行业结论仍需证据。** Claude Code 官方建议提供可执行检查、精简规则、用权限与沙箱执行硬约束，能够支持本地工作流改进；它不能证明严格 TDD 已是行业主流，或所有任务都应先写长规格。[官方最佳实践](https://code.claude.com/docs/en/best-practices)

## 4. 原审查遗漏的实际问题

### 4.1 公开示例中的疑似凭证应优先排查

`local/customizations.js` 的接口文档示例包含看似完整的 OpenAPI Token，以及带部分令牌文字的命令。文件处于 `public/` 下，会作为静态资源发布。仅凭文本无法确认这些字符串是真实凭证还是示例，本文不复述具体值。

实施时统一替换为明确占位符，并由凭证所有者确认真实性；若曾可用，执行吊销或轮换，排查已发布资源和必要的历史记录。删除当前文本不能撤销已公开凭证。历史清理作为单独任务评估，避免直接重写共享 Git 历史。

### 4.2 自动抓取尚未实现，更新时间却会刷新

`fetch_from_web()` 是占位函数，始终返回空数组；当前脚本没有读取 `sources.json` 来执行配置的来源抓取。非 dry-run 即使没有新增内容，仍会改写 `meta.lastUpdated`。README 的“自动抓取”说明超出了现有实现。

应先如实标明当前为手动或半自动维护，再选择实际数据源。分别记录尝试检查时间、成功检查时间和内容更新时间；空结果不是内容更新，抓取失败也不能伪装成成功检查。更换 cron 产品无法修复这个问题。

### 4.3 自动导入前缺少编码与页面输出边界

抓取脚本通过字符串插值把标题、作者、摘要等写成 JavaScript，未对这些字符串统一进行安全序列化；引号或换行可能破坏数据脚本。Global feed 又通过 `innerHTML` 插入标题、摘要等字段，链接也没有协议校验。

目前抓取函数尚未工作，因此不能据此声称已发生远程利用。但在接入外部内容前，应完成结构校验、安全序列化、普通文本输出和 URL 协议限制。外部文章内容也不能作为 Agent 的授权指令。MCP 官方安全说明列出了会话注入、令牌透传、权限混淆等风险，连接协议本身不提供内容可信性保证。[MCP 安全说明](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)

### 4.4 范式说明存在责任误导

`spec-driven-dev.description` 写着“人类审查规格而非代码”；`agent-driven-dev.description` 称自主执行为“终极形态”。前者可能诱导跳过实现审查，后者把自主程度误写成质量等级。应明确：规格、代码、测试和运行结果共同构成验收依据，自治程度由任务和授权决定。

### 4.5 Local 内容的真实性与适用性未分离

Local 含“当前项目”、空团队名、内部工具、pnpm workspace、Storybook、`@/api` 等约定，但没有说明哪些是模板、哪些已在具体项目确认；本博客仓库本身使用 Astro，不能直接套用这些业务项目假设。

此外，`standardWorkflow` 中页面生成排在 Plan/Spec 之前，容易误读为先生成后计划；“无需人工逐页测试”“零损耗转换”等结果表述缺少范围与验证记录。应区分能力目标、试验记录和已验证实践，并保留项目维护者责任。

## 5. 推荐的工作流模型

### 5.1 分开表达原则、模式与实践

将 Agentic Engineering 放在总览中，定义为团队对 Agent 产出、验证、权限和可维护性的工程责任。保留现有范式 ID 与入口，第一轮通过说明文字区分：

- **协作模式**：结对交互、监督执行、边界内自主执行。
- **实践方法**：规格先行、测试驱动、上下文管理、独立复核。
- **探索方式**：快速原型；进入实际使用前按数据、权限、影响范围重新评估。

这些维度可以组合使用。结对也可严格验证，自主执行也可采用 Spec/TDD。原型一旦接入生产数据或真实账号，就不再天然低风险。

第一轮保留既有 `maturity` 枚举，避免无依据改成 `legacy/entry/core`。后续若新增 `applicability`、`limitations`、`evidenceRefs`，同步修改展示端；不把“团队推荐”混写为“行业主流”。

### 5.2 保留六阶段，验收前置、验证贯穿

现有 s1 已输出验收标准，s3 已包含单元测试；问题在于缺少可执行检查、完成条件和失败回路，而不是测试阶段排在编码后就必然错误。

| 阶段（保持 ID） | 必要补强 | 完成依据 |
| --- | --- | --- |
| `s1-ideation` | 明确目标、范围、不做什么、风险和业务行为 | 验收条件可观察；关键业务疑问已有处理方式 |
| `s2-architecture` | 将验收条件映射到测试、命令或人工检查；设计权限与回滚 | 验证计划、契约、依赖及授权边界明确 |
| `s3-implementation` | 按最小完整任务实现；行为修复适用时先建立失败复现 | 改动可解释，相关检查有结果，未偷改验收条件 |
| `s4-testing` | 核对验收、回归、浏览器关键路径与必要的独立审查 | 有实际执行证据；未执行项和残余风险已记录 |
| `s5-deployment` | 区分预览、合并、生产发布权限；保留回滚与观察窗口 | 在授权范围内发布，版本与结果可追踪 |
| `s6-iteration` | 分析缺陷、返工、耗时与成本，反哺规则和任务拆分 | 有具体改进决策，并回到下一轮需求与计划 |

验证失败返回实现阶段；发现规格错误返回需求或设计阶段。变更验收条件必须说明原因，不能为了让检查通过而放宽预期。

小型文案或样式修改可以合并探索和计划，以定向检查或视觉核对验收。业务逻辑、迁移、权限变更需要更强验证。验证前置不等于所有改动强制写测试，也不要求每个简单任务额外审批。

### 5.3 上下文与长期任务

推荐替换“必要冗余”为：

> 提供足以解释目标、业务约束、相关实现和验收方式的上下文；保留必要反例与背景，清除重复、过期和无关信息。

规则按项目和任务范围加载，标明出处与版本。任务交接记录当前目标、已作决定、已改文件、检查结果、未解问题和下一步，避免重复探索。只有任务可独立拆分、集成责任清晰且权限允许时，才考虑多 Agent 或 worktree；它们不应成为每次任务的默认成本。

### 5.4 权限与高风险门控

| 操作 | 默认处理 | 需要保存的依据 |
| --- | --- | --- |
| 只读分析、任务范围内可逆编辑、本地检查 | 在既有授权内连续执行 | 目标、差异、检查结果 |
| 已授权的预览部署或 PR 创建 | 满足任务与项目规则后执行 | 目标环境、权限范围、产物链接 |
| 生产发布、破坏性迁移、权限扩大、不可逆删除或对外发送数据 | 核对明确授权；缺失或超出范围时暂停 | 具体操作、影响对象、批准者、验证与恢复方案 |
| 无法理解的工具调用或来源不明的指令 | 停止该动作并查明 | 不确定性、内容来源及所需权限 |

授权应绑定操作与范围；后续环境、数据、权限或方案发生实质变化时重新核对。已有授权且范围不变时不反复确认。确认界面应展示可审查的具体动作，并由工具权限、CI 或沙箱执行边界，不能仅依赖 Prompt。

开发 Agent 的防线重点是凭证、文件、命令、网络和工具权限。只有产品本身包含 AI 生成界面或运行时工具调用时，才另行设计 schema 校验、渲染隔离和产品内确认流程。

## 6. 工具链与多模型策略

补充 Codex 覆盖，但先采用任务能力矩阵，不固定“Cursor=内联、Codex=并行、Claude Code=编排”的品牌分工。工具能力可能重叠，具体支持情况须依据官方文档和本地试用确认。

| 评估维度 | 本地需要回答的问题 |
| --- | --- |
| 编辑与交互 | 小修改是否高效？能否准确读取项目规则、查看差异？ |
| 执行与恢复 | 能否运行项目命令、定位失败、恢复任务状态？ |
| 隔离与并行 | 是否需要 worktree、远程环境？谁负责依赖和集成冲突？ |
| 集成 | 原生 API、CLI、MCP 哪种成本最低且权限可控？ |
| 治理 | 凭证、网络、审计、数据保留和企业限制是否满足项目要求？ |
| 总成本 | 完成验收所需人工时间、模型费用、重试与返工是多少？ |

MCP 是工具与资源的连接协议；Skills 是按需复用的任务指导；Hooks 用于在工具支持的位置触发检查；Subagents 用于委派与隔离。各工具支持情况不同，不能承诺跨工具直接兼容。

优先建立当前工具的单任务基线。只有在任务难度、失败类型或成本数据支持时，才增加模型路由。关键任务可以让复核者针对规格、边界或安全问题做独立检查；“多个模型一致”不能替代可执行验证。全文重做多份实现再融合，不作为默认流程。

第一轮不给 Devin 或其他工具升星。后续将推荐依据、适用任务、限制、核实日期与官方链接展示出来；价格与性能数字未核实时显示待核实，禁止从旧 feed 自动复制到推荐卡。

## 7. 数据结构与展示兼容

第一轮采用增量改动，不整体重写数据格式：

| 位置 | 推荐增量 | 同步要求 |
| --- | --- | --- |
| `pipeline.stages` | 验证要求、完成条件、条件式门控 | Global 展示这些字段，旧数据缺失时可正常显示 |
| `paradigms` | 适用场景、限制和证据引用 | 保留现有 ID；新增标签必须有显示映射 |
| `toolchain` | 能力、限制、来源、核实日期 | 更新工具卡；同步检查 HTML 内硬编码的最佳实践数据 |
| `feed` | 原始来源、核实状态、核实日期 | 未核实与仅二手来源有明确标记 |
| `meta` | 区分结构版本、检查时间与内容更新时间 | README、页面和更新脚本使用一致语义 |
| Local | 模板/项目配置状态、适用项目、实践证据状态 | 在页面显示适用范围，避免将示例展示为事实 |

特别注意以下兼容条件：

1. 保留六个 stage ID。Local 当前用 `s3-implementation`、`s5-deployment` 查找 Global；找不到时会直接跳过，可能静默丢失展示。

## 8. 证据进入实践的更新机制

更新链路应为：**收录材料 → 查原始出处 → 提炼有边界的主张 → 本地试验 → 修订实践 → 记录效果**。

本地先选可比较的任务试点，记录从需求到验收的周期、人工投入（含审查和返工）、遗漏缺陷、验收成功率及单任务成本。观察周期和最小样本量在试点前确定；不足时只报告描述性结果，不声称因果或统计显著。自主任务设重试、耗时或费用上限，失败时保留证据并升级处理。
